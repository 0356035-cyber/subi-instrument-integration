# 数据模型

> **用途：** 核心对象、字段与表关系；新功能设计时对照。  
> **何时读：** 加表/加列、写 API 或 migration 前。  
> **关联：** 落点见 [代码地图.md](./代码地图.md)；权限规则见 [modules/权限与用户管理.md](./modules/权限与用户管理.md)。

**更新日期：** 2026-08-17
**策略：** 扩展优于重建；`project_id IS NULL` 仍为通用资料库。

---

## 1. 模型总览

```
Project（根）
├── Document[]              project_id 可空
├── ProjectMember[]         成员关系
├── ProjectTestStage[]      测试环节与负责工作人员
├── Schedule 域             访视/日历/排班表
├── DailyWorkLog[]          每日实绩，project_id 可空
├── MonthlyWorkReport       个人月报，不按项目拆分
├── Dataset[]               【阶段 4】
├── AnalysisTask[]          【阶段 5】
├── Report[]                【阶段 6】
├── AIWorkspace             【阶段 7】
└── StaffQualification      视图（数据在培训系统）
```

## 2. User — 用户

| 字段 | 说明 |
|------|------|
| `employee_id` | 工号，登录唯一键 |
| `full_name` | 姓名 |
| `role` | 系统角色：`admin` / `schedule_manager` / `system_maintainer` / `editor` / `viewer` |
| `job_title` | 业务职务（**不驱动权限**） |
| `department` / `phone` | 部门、电话；部门由标准目录多选，存储为兼容展示的 `、` 分隔文本 |
| `is_active` / `must_change_password` | 启用、强制改密 |

部门标准目录：`临床研究部`、`受试库`、`检测部（斑贴组）`、`检测部（防晒组）`、`质管部`、`皮肤科学创新转化部`、`统计室`、`办公室`。

## 3. Project — 项目

| 字段 | 说明 |
|------|------|
| `project_code` | 项目编号 |
| `name` | 项目名称 |
| `sponsor` | 申办方 |
| `claim_type` / `ethics_type` | 功效宣称（逗号分隔的多选值）、伦理类型 |
| `tags` | 标签 |
| `status` / `report_progress` | 项目状态；人工维护的报告进展（未启动 / 已完成草稿 / 已发申办方审核 / 已完成正式报告）。不替代阶段 6 的 Report 实体与归档记录。 |
| `summary` | 项目摘要或项目要求（历史字段名，界面不再称“项目简介”） |
| `trial_samples` | 试验样品说明 |
| `owner_employee_id` | **项目负责人工号** |
| `baseline_date` | 基线日 |
| `created_by` | 创建人工号 |
| `delete_requested_by` / `delete_requested_at` | 项目负责人提交的删除申请；科室主任或管理员确认后才删除 |

## 4.1 ProjectTestStage — 测试环节

| 字段 | 说明 |
|------|------|
| `project_id` | FK Project |
| `stage_type` / `name` | 环节类型与名称；类型包括临床评估、仪器检测、乳酸试验、自评问卷、产品使用、筛选问卷、其他 |
| `responsible_employee_id` | 负责工作人员工号；必须是项目负责人或项目成员 |
| `visit_node_codes_json` | 需执行该环节的项目访视节点 `node_code` 列表；使用稳定编码，避免访视节点编辑后数据库 ID 变化造成关联失效 |
| `description` | 环节说明 |
| `created_by` | 创建人工号 |

一个环节至少关联一个访视节点，只对应一名工作人员；一个工作人员可负责多个环节。测试环节用于定义应执行事项，不追踪过程状态、计划/完成日期或完成记录。已有数据库保留历史过程字段以兼容旧记录，但新 API 和页面不再读写。后续仪器管理上线后，再增加仪器关联，不在 Sub-I 中直接读写培训系统的仪器数据库。

## 5. Document — 资料

| 字段 | 说明 |
|------|------|
| `project_id` | 可空；空 = 通用库 |
| `document_group_id` | 版本组 |
| `title` / `category` / `version` | 标题、分类、版本号 |
| `document_type` | Protocol / SAP / CRF / Raw Data / Statistical Report 等 |
| `audience_scope` | `all_staff` / `project_leads_only`（部门内部要求） |
| `effective_date` / `status` | 生效日、现行/废止 |
| `content_text` / `file_path` | 全文、附件路径 |

### 通用库可见性（由 `permissions.py` 实现）

| 分类 | 可见范围 |
|------|----------|
| 法规与指南、伦理审查、培训课件 | 全员 |
| 模板下载中心 | 项目负责人及以上 |
| 部门内部要求 | 由 `audience_scope` 决定 |

## 6. AuditLog / ProjectLeadNotification

**AuditLog：** 主任/管理员修改他人项目时写入。

| 字段 | 说明 |
|------|------|
| `actor_employee_id` / `actor_role` | 操作人 |

## 7. OnlinePresence（当前访问人数）

`online_presence` 记录浏览器会话的 `employee_id`、随机 `session_id` 与 `last_seen_at`。页面每分钟发送心跳；系统以近 5 分钟内的不同工号数作为当前访问人数。该表仅用于短期在线统计，不保存访问历史；仅 `admin` / `schedule_manager` 可查看汇总人数。

## 8.1 工作日志与月报【第一期已实现】

与排班分离：周排班仍是计划，本域只存实绩和个人月报。

| 表 | 说明 |
|----|------|
| `daily_work_logs` | 按人、按日；可选 `project_id`；`quantity_text` 为手填完成情况 |
| `monthly_work_reports` | 按人、按 `YYYY-MM`；`summary_items_json` 由每日记录合并，其余栏目手写 |

`daily_work_logs` 主要字段：`employee_id`、`work_date`、`time_slot`、`project_id`、`source_availability_id`、`work_content`、`source_work_content`、`quantity_text`、`notes`。

`monthly_work_reports` 主要字段：`employee_id`、`year_month`、`full_name`、`job_title`、`status`、`summary_items_json`、`plan_items_json`、`issues_json`、`overtime_items_json`、`generated_at`。

合并键：有项目为 `(project_id, 工作内容)`，无项目为工作内容。加班不自动生成。

## 11. Report — 报告【阶段 6A/6B 已实现】

| 字段 | 说明 |
|------|------|
| `project_id` | FK；报告必须属于一个 Project |
| `title` / `report_number` | 报告名称与人工维护的报告编号 |
| `report_type` / `template_key` | 类型与固定模板键；首个为 `general_efficacy_v1` |
| `status` / `version` | 草稿或已生成草稿；每次重新生成草稿递增版本。正式审核/定稿流程后续接入 |
| `module_bindings_json` | 各模块选择的 Document / AnalysisTask ID、缺失确认、固定表格与试验方法区块人工字段及选择时版本快照 |
| `manual_content_json` | 各模块的人工补充文字；与资料引用分开保存 |
| `generation_log_json` | 模板键/版本、生成人、插入的结果表和草稿路径留痕；重生成保留最近历史 |
| `reviewed_by` / `reviewed_at` / `review_comment` | 为后续人工审核保留，6B 尚未开放定稿操作 |
| `generated_document_id` / `generated_file_path` | `generated_file_path` 指向 `uploads/reports/` 下的草稿；`generated_document_id` 待归档后回填 |

报告引用的资料与分析结果不复制到 `reports` 表：仅保存稳定 ID 和选定时的版本快照。来源 Document 必须属于当前项目或通用资料库；来源 AnalysisTask 必须属于当前项目且已执行并审核通过。

## 12. Staff & Qualification（联邦）

数据主存 **`instrument-training-home`**。Sub-I 仅存项目成员关系，经 BFF 查询资质。

### Instrument（培训系统主数据）

| 字段 | 说明 |
|------|------|
| `asset_code` | 稳定资产编号；既有数据迁移为 `EQ-<原ID>` |
| `category` / `manufacturer` / `model` | 设备分类、厂商与型号 |
| `serial_number` / `location` / `commissioned_date` | 序列号、位置、启用日期 |
| `responsible_person_id` / `status` | 设备负责人和状态（正常、维护中、校准中、维修中、停用） |

### InstrumentMaintenanceRecord（培训系统主数据）

| 字段 | 说明 |
|------|------|
| `instrument_id` | FK Instrument |
| `record_type` | 校准 / 维护 / 维修 / 核查 |
| `performed_date` / `next_due_date` | 执行日期与下次到期日期 |
| `result` / `service_provider` / `reference_number` / `notes` | 结果、服务方、凭证编号、说明 |
| `created_by` | 登记人；同步记录操作日志 |

## 13. Analysis V2 第一阶段增量字段

`analysis_tasks` 保持为 Analysis 的最小可执行单元；V2 不新增独立的设计、结果、产物或审核实体。

| 字段 | 说明 |
|------|------|
| `analysis_version` | 递增执行版本；首次成功执行为 1 |
| `executed_by` / `executed_at` | 当前版本的执行人和执行时间 |
| `execution_history_json` | 重跑前保存的结果、日志和审核快照 |
| `review_status` | 未提交 / 待审核 / 已通过 / 已驳回 |
| `reviewed_by` / `reviewed_at` / `review_comment` | 人工审核留痕；驳回必须有意见 |

执行状态仍使用既有 `status`（草稿、已执行）。项目负责人可提交审核；`admin` 和 `schedule_manager` 可审核。审核权限基于 `role`，不使用 `job_title`。
