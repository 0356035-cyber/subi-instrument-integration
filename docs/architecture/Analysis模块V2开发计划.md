# Analysis 模块 V2 开发计划

> 文档定位：本计划基于《未来临床研究AI平台蓝图》《开发治理规范》《Analysis模块演进设计评估》制定，用于后续 Analysis 模块迭代前的范围确认与实施依据。
>
> 约束：遵守渐进式演进原则；不重构整个 Analysis 模块；不引入复杂实体；所有能力继续以 Project 为边界。本文不代表立即开发。

> 实施状态：第一阶段已获批准并进入代码实施。数据库迁移采用增量字段方式；实际迁移仍由应用既有启动流程触发。

## 1. 开发目标

Analysis V2 的目标不是替换当前 Analysis MVP，而是在保留 `AnalysisTask + Dataset + result_json + log_json` 主链路的基础上，补足临床研究分析所需的治理语义、可追溯性和可扩展边界。

目标状态如下：

```text
已确认 Dataset
  -> Analysis Task
  -> 规则/统计 Engine 执行
  -> 结构化结果与执行日志
  -> 人工审核
  -> 仅审核后的结果可供 Report 引用
```

V2 重点服务于三件事：

- 让每次分析的输入、参数、执行版本、结果和审核情况可追溯。
- 让现有常规统计能力可以按统一约定逐步扩展。
- 为后续 Report 和 AI Workspace 提供可信、受审核的结果来源。

AI 只可解释已执行的分析结果或生成草稿；不得替代 Analysis Engine 计算、统计判断或人工审核。

## 2. 第一阶段范围

第一阶段定位为“Analysis 治理与可用性增强”，只围绕现有 Project - Dataset - AnalysisTask 链路小步改进。

纳入范围：

- 明确任务状态和审核状态的业务语义。
- 补充执行人、执行时间、分析版本和审核意见等最小留痕。
- 规范现有三类分析的输入、参数、结果和日志格式。
- 优化项目内分析任务列表、任务详情和结果查看体验。
- 约束未来 Report 只能引用审核通过的分析结果。

继续保留：

- 已确认 Dataset 才能作为分析输入的规则。
- 每个任务绑定一个 Project、一个数据集、一个分析类型和一组参数的模式。
- 当前配对比较、变化率、有效率三类分析能力。
- `parameters_json`、`result_json`、`log_json` 作为早期的灵活扩展容器。

第一阶段不纳入：

- 新建独立的 `AnalysisDesign`、`AnalysisResult`、`AnalysisArtifact`、`AnalysisReview` 表。
- 复杂多终点、多重比较、重复测量、回归或生存分析。
- VISIA、OCT 图像或二进制设备文件处理。
- AI 自动生成统计结论、自动审核或自动定稿报告。
- 对现有分析引擎进行整体重写。

## 3. 数据模型调整建议

### 3.1 保持现有模型

继续以 `AnalysisTask` 作为最小可执行单元，保留：

- `project_id`：Project 中心化边界。
- `dataset_id`：已确认数据集来源。
- `analysis_type`：分析类型标识。
- `variable_column`、`baseline_visit`、`comparison_visit`：当前单指标、两时间点分析的必要参数。
- `parameters_json`：类型专属参数。
- `result_json`：结构化分析结果。
- `log_json`：执行环境、数据映射和计算过程留痕。
- `created_by`、`reviewed_by`：创建与审核人员基础。

### 3.2 按需增加的轻量字段

后续进入实现前，应先确认真实审核流程，再评估以增量迁移方式补充以下字段：

| 字段 | 用途 | 第一阶段建议 |
|---|---|---|
| `executed_by` | 记录执行人 | 建议增加 |
| `executed_at` | 记录实际执行时间 | 建议增加 |
| `analysis_version` | 标识规则或算法版本 | 建议增加 |
| `review_status` | 草稿、待审核、已通过、已驳回等审核语义 | 建议增加 |
| `reviewed_at` | 记录审核时间 | 建议增加 |
| `review_comment` | 保存审核意见或驳回原因 | 建议增加 |
| `locked_at` | 被报告引用或定稿后保护结果 | 后续按 Report 需求增加 |

不建议在第一阶段新增 `design_id`、通用数据源多态字段或复杂外键关系。多指标、多数据源或多任务方案确有稳定业务需求后，再将 Analysis Design 等概念独立为实体。

### 3.3 JSON 使用约定

短期内保留 JSON，避免为尚未稳定的分析类型过早建表：

- `parameters_json`：保存分析类型专属参数、筛选条件和显示偏好。
- `result_json`：保存摘要、统计量、结果表、样本量、缺失情况和可引用标识。
- `log_json`：保存数据集版本标识、映射、运行时依赖版本、方法选择和纳入排除信息。

审核状态、执行人、执行时间、版本和锁定状态属于高频筛选和审计信息，应优先使用结构化字段保存。

## 4. 页面优化方案

页面继续位于 Project 的 Analysis Tab，不创建独立应用或独立工作台。

任务列表应突出项目管理所需信息：任务名称、数据集、分析类型、目标指标、执行状态、审核状态、分析版本、执行时间和审核人；支持按状态筛选并快速进入详情。

创建与编辑页面应保持当前表单模式，但根据分析类型动态展示必要参数，并在提交前提示：数据集必须已确认、时间点与指标必须来自已映射列、执行后修改参数需要形成新的可追溯执行记录或先退回任务。

结果详情建议按以下顺序显示：

```text
任务基本信息
-> 输入数据与参数摘要
-> 规则计算结果与统计表
-> 样本纳入/排除与缺失提示
-> 执行日志与版本信息
-> 审核记录与报告可用状态
```

审核区只提供明确的人工动作，例如提交审核、通过、驳回和填写意见；不把 AI 输出当作审核动作。

## 5. API 调整方案

保持现有 Project 作用域 API 和任务 CRUD 路由，不调整前端只经由 Sub-I 后端访问的边界。

建议以兼容方式增量调整：

- 在任务读取接口返回执行、审核、版本和锁定相关字段。
- 在创建与更新接口校验任务可编辑状态；已执行或已审核任务不应静默覆盖历史结果。
- 将执行接口的返回统一为任务状态、结果摘要、日志摘要和版本信息。
- 增加轻量审核动作接口，或在现有更新接口中以受限字段完成审核；最终选择以现有路由风格为准。
- 为未来 Report 预留“可引用结果”查询条件，但第一阶段不开发 Report 功能。

接口不应接受 AI 直接写入审核状态、最终结论或报告定稿状态。

## 6. Analysis Engine 优化方案

不替换现有 `runner.py`，而是在其内部逐步形成轻量注册约定。每种分析类型至少定义：

| 内容 | 要求 |
|---|---|
| 类型标识 | 稳定、可版本追踪，例如 `paired_comparison` |
| 输入要求 | 必需列、数据类型、是否需要访视或分组列 |
| 参数规则 | 必填参数、默认值、允许范围 |
| 校验逻辑 | 输入数据、映射和参数校验 |
| 执行逻辑 | 明确的规则计算或统计方法 |
| 结果结构 | 摘要、统计量、表格、样本情况、限制提示 |
| 日志结构 | 数据来源、映射、版本、方法选择、异常信息 |
| 版本标识 | 规则或算法版本，供结果追溯 |

先将现有配对比较、变化率和有效率纳入同一约定，验证其稳定性后，再按实际项目需求增加：常规统计、问卷计分、功效评价，以及基于真实导出格式的 VISIA 或 OCT 分析。

不引入动态代码加载、外部插件市场或复杂任务队列。当前所谓“模块化”是 Analysis 内部的清晰注册边界，而非新增服务。

## 7. 数据迁移风险

数据变更必须使用明确的迁移逻辑，不手工修改真实数据库。主要风险如下：

| 风险 | 影响 | 控制方式 |
|---|---|---|
| SQLite 增列兼容 | 历史任务缺少新字段 | 使用可空字段或明确默认值，旧记录可正常读取 |
| 状态语义变化 | 旧“已执行”任务无法直接判断审核状态 | 明确迁移映射，避免把历史任务自动标为“已审核” |
| JSON 结构演进 | 旧结果无法被新页面完整展示 | 新读取逻辑兼容旧结构；不批量覆写历史 JSON |
| 重新执行覆盖 | 报告或审核依据被替换 | 审核后限制修改；后续按需要支持新执行记录或锁定 |
| 数据集版本不清 | 结果无法复现 | 在新执行日志中记录数据集版本标识或文件指纹；历史数据不追溯补造 |

迁移前应准备脱敏样例库验证，并确认不涉及生产数据库、业务附件或未备份数据。

## 8. 测试方案

实施时按风险分层验证，且不得在未确认数据隔离条件下运行会写入业务库的脚本。

- 单元测试：参数校验、数据列校验、三类既有分析的结果结构、版本和日志生成。
- API 测试：Project 权限、仅已确认 Dataset 可执行、状态流转、审核动作和只读保护。
- 兼容性测试：历史 `AnalysisTask`、旧 `result_json`、旧 `log_json` 的读取与显示。
- 人工页面验证：创建、执行、查看、提交审核、通过、驳回、筛选和权限提示。
- 数据安全验证：确认测试使用内存数据库或隔离数据库；不读取、写入或清理真实业务库和上传附件。
- 回归验证：现有配对比较、变化率、有效率的数值结果与既有版本一致，或对差异给出经过确认的规则说明。

## 9. 分阶段实施步骤

### 阶段 A：方案确认与治理定义

目标：确认状态机、角色权限、审核责任、结果可引用规则和字段最小集。

收益：先固定业务语义，避免把审核逻辑散落在页面和引擎中。

风险：若未与实际研究流程核对，状态可能过度设计。

交付：字段说明、状态流转图、接口影响清单和测试用例清单。

### 阶段 B：最小留痕与审核能力

目标：以增量方式补齐执行、版本和审核留痕，保持旧任务可读。

收益：Analysis 结果可以成为后续 Report 的可信输入。

风险：数据库迁移和历史状态映射需要谨慎验证。

交付：最小模型迁移、受控 API、项目内审核入口和兼容性测试结果。

### 阶段 C：统一现有 Engine 约定

目标：将现有三类分析整理为统一的输入校验、参数、结果、日志和版本协议。

收益：后续扩展不会破坏现有 Project - Dataset - Analysis 主链路。

风险：结果 JSON 格式调整可能影响页面和未来报告引用。

交付：分析类型注册约定、三类既有分析适配结果和回归测试结果。

### 阶段 D：基于真实需求的能力扩展

目标：优先从结构化 Excel 数据切入问卷、功效评价或常规统计；仪器分析只在获得真实样例和流程后试点。

收益：用真实研究场景验证扩展边界，避免抽象出无人使用的平台。

风险：VISIA、OCT 等数据格式、图像文件和算法版本差异可能提高复杂度。

交付：经业务确认的单一分析类型试点，以及其输入约束、审核流程、结果格式和报告引用规则。

### 阶段 E：与 Report、AI Workspace 受控联动

目标：Report 只选择审核通过且未被不当覆盖的 Analysis 结果；AI 只读取可追溯来源并输出待审核草稿。

收益：形成“资料 - 数据 - 分析 - 审核 - 报告”的 Project 内闭环。

风险：如果先接入 AI 再建立审核留痕，会削弱临床研究结论的可信性。

交付：Analysis 到 Report 的引用规则、AI 输出审计字段和人工审核流程。

## 结论

Analysis V2 应被视为当前 MVP 的治理和扩展准备工作，而不是一次架构替换。近期优先级是让现有分析任务的状态、版本、输入、结果和审核链条可说明、可追溯、可供 Report 安全引用；统计方法、问卷和仪器能力则应以真实项目数据和明确业务流程为触发条件逐步增加。
