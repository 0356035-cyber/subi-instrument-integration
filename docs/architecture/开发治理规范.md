# 开发治理规范

> 本文档用于约束未来所有开发任务，确保系统持续沿着 Project 中心化临床研究 AI 平台方向演进。  
> 本文档不是技术教程，不替代具体模块设计、代码地图或测试说明；它是 Codex、开发人员和 AI 助手在修改代码前必须参考的设计约束。

---

## 一、文档定位

### 1.1 用途

本规范用于回答未来开发前必须先判断的问题：

- 这个需求是否应挂到 Project 下？
- 是否破坏 Sub-I 与仪器培训系统的独立边界？
- 是否需要新增模块、扩展已有模块，还是只更新文档和配置？
- 是否需要新增数据库实体？
- 是否涉及真实业务数据、附件、数据库文件或 `.env`？
- 是否让 AI 越过规则计算和人工审核边界？

### 1.2 适用对象

本规范适用于：

- Codex。
- 开发人员。
- AI 助手。
- 后续维护者。
- 参与需求设计、架构评审、测试验证和部署更新的人员。

### 1.3 使用时机

在以下动作前必须参考本规范：

- 新增功能。
- 修改数据库结构。
- 新增或调整模块边界。
- 接入新仪器数据。
- 扩展 Analysis、Report 或 AI Workspace。
- 改动权限、项目、资料、数据集、分析、报告等核心链路。
- 执行可能影响业务数据、附件、配置、迁移、启动或部署的操作。

## 二、系统演进原则

### 2.1 Project 优先原则

所有新能力优先挂载到 Project 下。

应遵守：

- 项目资料、数据集、分析任务、报告、AI 解释、仪器检测数据，默认都应有 Project 上下文。
- 新页面优先进入项目详情 Tab 或项目工作流。
- 新 API 优先采用 `/projects/{project_id}/...` 结构。
- 新数据库实体如果属于研究项目过程，应优先包含 `project_id`。

禁止：

- 为单一新能力随意创建新的独立系统。
- 绕过 Project 单独建设平行业务入口。
- 把未来 Subject、Sample、InstrumentMeasurement、Report、AI 输出做成与 Project 脱离的孤立对象。

### 2.2 双系统边界原则

仪器培训系统继续保持独立。

应遵守：

- `instrument-training-home` 负责人员、仪器、培训、考核、授权和资质事实。
- `subi_knowledge_platform` 负责项目、资料、排班、Dataset、Analysis、Report、AI Workspace 和项目内资质视图。
- Sub-I 通过 BFF 查询培训系统资质。
- 人员关联统一使用 `employee_id`。

禁止：

- 将培训系统合并进 Sub-I。
- Sub-I 直接写培训系统数据库。
- Sub-I 前端直接调用培训 API。
- 为方便开发复制培训系统全表到 Sub-I。

### 2.3 数据与代码分离原则

业务数据、附件、真实配置和数据库文件不得进入代码仓库。

应保护：

- `subi_knowledge_platform/data/`
- `instrument-training-home/data/`
- `subi_knowledge_platform/uploads/`
- `backups/`
- `.env`
- `.env.tunnel`
- `subi_knowledge_platform/.env`

禁止：

- 提交 `.db` 文件。
- 提交 uploads 附件载荷。
- 打印、复制、解析真实 `.env` 内容。
- 用 Git checkout/reset 恢复数据库文件。
- 未确认就运行恢复脚本或写库冒烟脚本。

### 2.4 渐进式演进原则

系统应在现有稳定能力上小步扩展。

应优先：

- 扩展现有 Project、Document、Dataset、Analysis、Report 规划模块。
- 使用现有 FastAPI、Streamlit、SQLite、Docker Compose 架构。
- 为新域创建独立模块，而不是堆叠到主入口。
- 保持四容器和双系统独立部署。

禁止：

- 无必要的大规模重构。
- 整体重写系统。
- 过早引入复杂微服务、消息队列、Kubernetes 或插件市场。
- 为尚未验证的业务想象一次性建立完整临床数据仓库。

### 2.5 AI 边界原则

AI 是辅助层，不是最终决策层。

AI 可以：

- 理解项目资料。
- 提取 Protocol / SAP / CRF 中的研究设计、终点、访视和统计方法。
- 起草分析计划。
- 对规则引擎结果生成解释草稿。
- 辅助报告文字润色。
- 做项目资料问答。

AI 不能：

- 替代规则计算。
- 决定最终统计结论。
- 自动确认 P 值、显著性、功效评价结论。
- 自动剔除样本或确认分析人群。
- 无人工审核生成最终报告。
- 绕过 AnalysisTask 和 Report 审核流程直接写定稿结论。

## 三、新功能设计流程

任何新增功能进入代码实现前，应按以下流程推进：

```text
需求分析
  ↓
业务设计
  ↓
架构评估
  ↓
数据模型设计
  ↓
开发计划
  ↓
代码实现
  ↓
测试验证
```

### 3.1 需求分析

输出：

- 需求背景。
- 目标用户。
- 解决的问题。
- 是否属于当前阶段。
- 是否必须现在做。
- 是否涉及业务数据、附件、权限、数据库、部署或 AI。

必须判断：

- 是否符合 Project 中心方向。
- 是否属于 Sub-I、培训系统还是根目录部署文档。
- 是否可能与现有模块重复。

### 3.2 业务设计

输出：

- 业务流程。
- 主要页面或操作入口。
- 角色与权限边界。
- 输入、输出和状态流。
- 人工审核节点。

必须说明：

- 新能力挂载在哪个 Project 工作流下。
- 是否影响现有项目详情 Tab。
- 是否需要与培训资质联动。

### 3.3 架构评估

输出：

- 影响模块。
- 是否扩展已有模块或新增模块。
- 是否影响双系统边界。
- 是否影响部署、启动、备份、恢复。
- 是否需要更新架构文档。

必须避免：

- 新建第三套应用。
- 跨系统直接耦合数据库。
- 将新域堆叠进 `backend/main.py` 或 `frontend/app.py`。

### 3.4 数据模型设计

输出：

- 新增或变更的数据实体。
- 字段清单。
- 外键关系。
- 状态流。
- JSON 字段使用理由。
- 版本和审计需求。
- 迁移方案。

必须判断：

- 是否真的需要新增实体。
- 是否可以先扩展 Document、Dataset、AnalysisTask 或 Report。
- 哪些信息必须结构化保存。
- 哪些信息可以暂存 JSON。

### 3.5 开发计划

输出：

- 修改文件清单。
- 新增文件清单。
- 不修改范围。
- 实施步骤。
- 测试方式。
- 风险说明。
- 回滚或恢复注意事项。

涉及高风险操作时，必须先获得用户确认。

### 3.6 代码实现

要求：

- 小步修改。
- 遵循现有目录和命名。
- 新域优先使用 `backend/<domain>/`、`frontend/*_pages.py`。
- 数据库变更必须有明确迁移逻辑。
- 不修改业务数据库内容。
- 不覆盖真实配置。

### 3.7 测试验证

输出：

- 已运行测试。
- 未运行测试的原因。
- 是否涉及真实 API。
- 是否写入业务数据库。
- 是否需要人工界面验证。
- 是否需要同步文档。

测试应按风险分级执行：纯内存测试、真实 API 测试、写库冒烟脚本必须区分。

## 四、模块设计规范

### 4.1 什么时候应该新增模块

满足以下条件之一，可以考虑新增模块：

- 形成独立业务域，如 Report、AI Workspace、Subject、InstrumentMeasurement。
- 有独立 API、CRUD、迁移、页面和权限逻辑。
- 逻辑继续放入现有文件会使 `main.py`、`app.py` 或某个模块明显膨胀。
- 未来会持续扩展，且需要独立测试和文档。

推荐落点：

```text
subi_knowledge_platform/backend/<domain>/
subi_knowledge_platform/frontend/<domain>_pages.py
docs/modules/<模块>.md
```

### 4.2 什么时候应该扩展已有模块

满足以下条件之一，应优先扩展已有模块：

- 只是 Project、Document、Dataset、Analysis、Report 的小范围能力增强。
- 只是已有实体增加字段、状态或筛选。
- 只是已有页面增加一个操作或视图。
- 只是 Analysis 新增一种内部分析类型。
- 只是 Report 新增一种模板类型。

示例：

- 新增一种常规统计方法：优先扩展 Analysis。
- 新增报告模板类型：优先扩展 Report。
- 新增项目资料类型：优先扩展 Document。
- 新增 Excel 数据映射规则：优先扩展 Dataset。

### 4.3 什么时候应该新增数据库实体

满足以下条件之一，可以考虑新增实体：

- 该对象有独立生命周期。
- 该对象需要被多个模块引用。
- 该对象需要权限控制、状态流、审计或版本。
- 该对象需要被查询、筛选、统计。
- 该对象不能稳定表达在现有实体或 JSON 字段中。

未来可能新增实体：

- `Subject`：受试者管理稳定后。
- `StudyVisit` / `Timepoint`：访视与数据分析需要统一引用时。
- `Sample`：样品采集与流转进入系统时。
- `ProjectInstrument`：项目仪器清单稳定后。
- `InstrumentMeasurement`：VISIA/OCT 等检测记录进入系统时。
- `DeviceDataFile`：设备原始文件需要统一管理时。
- `Report`：报告生成进入开发阶段时。
- `AIActionLog`：AI Workspace 启动时。
- `ReviewRecord`：审核流程超出现有状态字段表达能力时。

### 4.4 什么时候不应该新增实体

以下情况不应新增实体：

- 只是临时展示字段。
- 只是一次性导入的中间结果。
- 业务流程尚未验证。
- 真实数据样本尚不明确。
- 可以由 Document、Dataset、AnalysisTask 或 Report 承载。
- 只是为了“未来可能用到”而抽象。

### 4.5 核心对象治理

Project：

- 新能力默认挂 Project。
- Project 是权限、上下文、数据追溯和 AI 上下文边界。

Document：

- 继续承载通用资料和项目资料。
- `document_type` 用于区分 Protocol、SAP、CRF、Raw Data、Statistical Report 等。
- 定稿报告应归档为 Document。

Dataset：

- 作为结构化数据入口。
- 适合 Excel、问卷、设备导出表。
- 确认映射后才能进入 Analysis。

Analysis：

- 作为规则统计和功效评价入口。
- 所有结果必须留痕。
- 新分析能力应先走内部扩展，而不是新建平行分析系统。

Report：

- 作为报告生成、审核和归档闭环。
- 必须引用 Project、Analysis 结果和模板。
- 定稿必须人工审核。

AI Workspace：

- 作为辅助理解和草稿生成空间。
- 不直接写最终统计结论。
- 不替代 Report 审核。

Subject / InstrumentMeasurement：

- 等真实业务流程和数据样本稳定后逐步引入。
- 不为尚未验证的仪器流程提前建设通用大平台。

## 五、数据库设计原则

### 5.1 数据表设计原则

每张新表应明确：

- 业务对象。
- 所属 Project。
- 主键。
- 状态字段。
- 创建人。
- 创建时间。
- 更新时间。
- 审计或版本需求。

项目相关表默认应包含：

- `project_id`
- `created_by` 或等价字段
- `created_at`
- `updated_at`

### 5.2 外键关系原则

应遵守：

- Project 是项目研究数据的根。
- Dataset 应关联 Project。
- AnalysisTask 应关联 Project 和 Dataset。
- Report 应关联 Project，并记录来源 Analysis。
- InstrumentMeasurement 未来应关联 Project，并在成熟后关联 Subject、Timepoint、Sample 或 DeviceDataFile。

跨系统关系：

- Sub-I 不直接外键关联培训系统数据库。
- 与培训系统人员、仪器、授权的关联通过 `employee_id`、仪器标识和 BFF 查询结果表达。

### 5.3 JSON 字段使用原则

JSON 字段可以用于：

- 早期扩展参数。
- 分析参数。
- 数据集映射。
- 执行日志。
- 第三方或设备导出中的非稳定字段。
- 暂未确定结构的 AI 输出元数据。

JSON 字段不应用于长期保存：

- 需要频繁查询和筛选的字段。
- 权限判断字段。
- 状态流字段。
- 审核结论。
- 关键业务编号。
- 与 Project、Dataset、Analysis、Report 的核心关系。

### 5.4 必须结构化保存的信息

以下信息必须结构化：

- Project 归属。
- 用户、负责人、成员。
- 文档类型和版本组。
- Dataset 状态。
- Analysis 类型、状态、数据集来源、执行人。
- Report 状态、模板、来源分析、定稿文件。
- 审核人、审核状态、审核时间。
- AI 输出的来源资料、模型版本、输出时间和人工审核结果。

### 5.5 可以暂存在 JSON 中的信息

以下信息可以暂存在 JSON：

- Dataset 列映射。
- Analysis 扩展参数。
- Analysis 运行日志。
- 分析结果表的结构化输出。
- 设备专属的早期导入元数据。
- AI 草稿的引用片段信息。

当 JSON 中某个字段开始被频繁查询、筛选、统计或用于权限判断时，应评估是否结构化。

### 5.6 数据版本和审计要求

必须保留追溯能力：

- Document 使用 `document_group_id` 管理版本。
- Analysis 使用 `result_json` 和 `log_json` 记录结果与执行过程。
- Report 应记录生成日志、来源分析和定稿版本。
- AI 输出应记录来源、任务、模型、时间和人工采纳情况。
- 主任或管理员跨负责人修改项目相关内容时，应记录审计或通知。

## 六、Analysis 模块设计规范

### 6.1 模块定位

Analysis 是规则计算和功效评价层，不是 AI 层。

它负责：

- 接收已确认 Dataset。
- 保存分析参数。
- 调用明确的规则或统计方法。
- 输出结构化结果。
- 保存完整执行日志。
- 支持人工审核。

### 6.2 输入数据要求

未来分析任务必须满足：

- 数据来源属于某个 Project。
- Dataset 已确认。
- 关键列映射已完成。
- 分析人群、终点、访视、变量、阈值等参数明确。
- 若来自仪器数据，应说明设备来源、文件版本和处理规则。

VISIA、OCT、问卷、功效评价等分析接入时，应先定义输入数据形态，再开发分析逻辑。

### 6.3 分析类型注册

新增分析类型应进入统一的 Analysis 扩展边界。

每种分析类型应定义：

- 类型 ID。
- 显示名称。
- 输入要求。
- 参数 schema。
- 校验逻辑。
- 执行函数。
- 结果格式。
- 日志格式。
- 是否需要人工审核。

不应为每种分析类型新建一套平行系统。

### 6.4 参数保存

必须结构化保存：

- `analysis_type`
- `dataset_id`
- `project_id`
- `population`
- `endpoint`
- `baseline_visit`
- `comparison_visit`
- `variable_column`
- `alpha`
- `status`

可以暂存于 JSON：

- 阈值。
- 成功判定规则。
- 设备专属参数。
- 问卷计分规则。
- 早期扩展参数。

### 6.5 结果保存

分析结果应写入结构化 JSON，并尽量包含：

- 分析类型。
- 指标名称。
- 样本量。
- 描述统计。
- 检验方法。
- P 值或置信区间。
- 结果表。
- 可供 Report 引用的表格结构。

结果不应只保存为自然语言描述。

### 6.6 日志保存

`log_json` 或等价日志必须记录：

- 执行时间。
- 执行人或任务触发人。
- 数据集 ID 和状态。
- 分析参数。
- 数据映射。
- 样本量和缺失处理。
- 统计方法选择依据。
- Python 包或算法版本。
- 设备算法版本。
- 错误或警告。

### 6.7 版本追踪

未来分析模块应能追踪：

- Dataset 版本或文件。
- 分析参数版本。
- 分析算法版本。
- 依赖包版本。
- 设备数据版本。
- 结果生成时间。

如果结果用于报告，应保证报告能回溯到对应 AnalysisTask。

### 6.8 人工审核

Analysis 结果不得自动等同于最终结论。

应支持：

- 草稿。
- 已执行。
- 待审核。
- 已审核。
- 已驳回。
- 被 Report 引用。

当前状态较轻时，可以先保持简单状态，但进入报告和 AI 解释阶段前，应补齐审核语义。

## 七、Report 模块设计规范

### 7.1 报告生成链路

报告生成必须遵循：

```text
Analysis 结果
  +
Word 模板
  +
AI 辅助文字草稿
  +
人工审核
  +
最终归档 Document
```

### 7.2 Report 模块职责

Report 应负责：

- 选择报告类型。
- 选择模板。
- 选择来源 AnalysisTask。
- 填充项目基本信息。
- 插入分析结果表。
- 记录生成日志。
- 生成 docx 草稿。
- 支持人工审核。
- 定稿后归档为项目 Document。

### 7.3 AI 在 Report 中的边界

AI 可以：

- 起草 Results 或 Discussion 文本。
- 润色人工撰写内容。
- 检查报告与来源资料的一致性。
- 提醒缺失分析或资料。

AI 不能：

- 直接生成最终报告。
- 自动签发报告。
- 覆盖统计结论。
- 绕过人工审核。
- 自由决定模板结构和关键结论。

### 7.4 定稿与归档

报告定稿必须：

- 经过人工审核。
- 记录审核人。
- 记录审核时间。
- 记录来源 AnalysisTask。
- 记录生成日志。
- 归档为项目 Document。
- 使用合适的 `document_type`，如 `Statistical Report`。

## 八、AI 能力接入规范

### 8.1 AI 可以做什么

AI 可用于：

- 阅读和总结 Protocol、SAP、CRF。
- 提取研究设计、终点、访视和统计方法。
- 生成分析计划草稿。
- 解释规则引擎已生成的结果。
- 生成报告文字草稿。
- 辅助项目资料问答。
- 发现资料缺口、映射疑点、报告不一致。

### 8.2 AI 不能做什么

AI 不得：

- 决定最终统计结论。
- 替代规则引擎计算。
- 替代统计审核。
- 替代项目负责人审核。
- 自动定稿报告。
- 直接修改业务数据库。
- 直接修改权限。
- 直接删除、覆盖业务附件。

### 8.3 AI 输出记录要求

未来 AI 输出必须记录：

- 来源资料。
- 使用任务。
- 关联 Project。
- 关联 Document。
- 关联 Dataset 或 AnalysisTask。
- 模型版本。
- 输出时间。
- Prompt 类型或任务类型。
- 输出内容。
- 人工审核结果。
- 是否采纳。

### 8.4 AI 输出状态

AI 输出默认状态应为：

- 草稿。
- 建议。
- 待人工确认。

除非经过明确审核流程，AI 输出不得进入定稿状态。

## 九、Codex 开发规范

### 9.1 修改代码前必须执行

Codex 修改代码前必须：

1. 阅读相关架构文档  
   至少包括 `AGENTS.md`、`README_FOR_CODEX.md`、`PROJECT_STATUS.md`、`docs/开发规范.md`，以及与任务相关的模块文档、架构评估或蓝图。

2. 明确修改影响范围  
   说明涉及 Sub-I、培训系统还是根目录；是否涉及数据库、附件、真实配置、权限、部署或 AI。

3. 输出实施计划  
   说明准备修改哪些文件、为什么修改、验证方式和风险。

4. 等确认后再修改  
   涉及数据库结构、真实业务数据、附件、`.env`、Docker、迁移、备份恢复、写库脚本或高风险权限变化时，必须等待用户确认。

### 9.2 修改过程中必须遵守

- 不进行无关重构。
- 不覆盖用户已有改动。
- 不读取真实 `.env` 内容。
- 不枚举敏感业务数据和附件细节。
- 不擅自运行 Docker、pytest、迁移或冒烟脚本。
- 不用 Git 操作恢复数据库文件。
- 不配置 `safe.directory`，除非用户明确要求。

### 9.3 修改完成后必须说明

交付说明必须包含：

- 修改文件。
- 修改原因。
- 测试方式。
- 未测试原因。
- 潜在影响。
- 是否涉及数据库。
- 是否涉及上传/下载。
- 是否涉及权限。
- 是否涉及部署。
- 后续建议。

如果完成的是文档任务，也应说明：

- 创建或修改的文档位置。
- 参考文档。
- 核心结论。

## 十、当前禁止事项

当前阶段禁止：

- 重写系统。
- 合并 Sub-I 与仪器培训系统。
- 新建第三套应用绕开现有架构。
- 过早引入复杂微服务。
- 过早引入 Kubernetes、消息队列、分布式任务系统。
- 过早建设完整 LIMS。
- 每人独立子库。
- AI 自动生成最终科研结论。
- AI 自动签发报告。
- 无人工审核发布统计结论。
- 未验证业务需求前设计通用仪器平台。
- 在没有真实设备数据样本前设计全量 VISIA/OCT 通用接入体系。
- 将新功能继续堆叠到 `backend/main.py` 或 `frontend/app.py`。
- 直接修改生产数据库。
- 提交 `.db`、uploads、真实 `.env` 或密钥。
- 未确认就运行恢复脚本、写库冒烟脚本、Docker 构建或生产迁移。

## 十一、治理结论

未来开发的核心判断标准是：是否让系统更像一个以 Project 为中心、规则计算可追溯、AI 辅助但不越界、报告可审核归档的临床研究平台。

符合这个方向的功能，可以渐进式推进；偏离这个方向、破坏双系统边界、削弱数据安全、绕过人工审核或造成过度设计的功能，应暂缓或拒绝。
