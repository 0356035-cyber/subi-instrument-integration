# 项目未来演进架构适配评估报告

> 评估范围：基于当前文档体系、代码结构、数据库模型、模块划分与部署架构，对项目未来演进为以 Project 为核心的临床研究 AI 平台的适配性进行分析。  
> 评估边界：本报告仅做架构分析与评估，不提出推翻现有系统的重构方案，不修改代码，不新增功能。

---

## 1. 当前系统架构总结

### 1.1 当前整体技术架构

当前项目采用“整合仓 + 两个独立子系统 + Docker Compose 四容器”的架构：

- 根目录 `D:\projects`：负责 Docker Compose、启动脚本、备份恢复脚本、部署文档和接管规范。
- `subi_knowledge_platform`：Sub-I 临床研究资料库，已逐步扩展为 Project 中心的临床研究项目平台雏形。
- `instrument-training-home`：仪器培训、考核、授权与资质管理系统，保持独立。

技术栈：

- 后端：FastAPI。
- 前端：Streamlit。
- 数据库：SQLite。
- ORM：Sub-I 使用 SQLAlchemy；培训系统使用 SQLAlchemy 2.x。
- 部署：Docker Compose 四容器。
- 认证：JWT，人员关联统一使用 `employee_id`。

文字版架构图：

```text
用户浏览器
├── Training UI :8501
│   └── Training API :8000
│       └── instrument_training.db
│
└── Sub-I UI :8510
    └── Sub-I API :8001
        ├── subi_knowledge.db
        ├── uploads/
        └── BFF: /integrations/training/*
            └── Training API :8000
```

部署拓扑：

```text
D:\projects
├── docker-compose.yml
├── scripts/
├── docs/
├── subi_knowledge_platform/
│   ├── backend/
│   ├── frontend/
│   ├── data/subi_knowledge.db
│   └── uploads/
└── instrument-training-home/
    ├── app/
    ├── streamlit_app/
    └── data/instrument_training.db
```

### 1.2 前后端结构

Sub-I：

- 后端入口仍是 `backend/main.py`，但 Dataset、Analysis、Schedule、Integrations 等域已部分拆到独立模块。
- 前端主壳是 `frontend/app.py`，项目、排班、资质、Dataset、Analysis 等页面已拆为独立页面文件。
- 已形成“主入口注册 + 业务域模块”的过渡架构。

培训系统：

- 后端 `app/main.py` + `app/api/v1/` 路由。
- 前端 `streamlit_app/` 按人员、仪器、培训、考核、授权、导入、统计等页面拆分。
- 业务模型围绕用户、仪器、培训记录、考核记录、授权记录展开。

### 1.3 数据存储方式

当前业务数据和代码明确分离：

- Sub-I 数据库：`subi_knowledge_platform/data/subi_knowledge.db`。
- 培训数据库：`instrument-training-home/data/instrument_training.db`。
- Sub-I 附件：`subi_knowledge_platform/uploads/`。
- 业务数据库、附件、真实 `.env` 均不应进入 Git。

当前 SQLite 足够支持部门内部、小团队、单机或 NAS 部署场景；未来若进入多项目、多仪器、高并发和更多自动化分析阶段，SQLite 可能成为并发、迁移治理和审计查询方面的瓶颈。

### 1.4 模块划分

Sub-I 当前核心模块：

- 用户与认证：`auth.py`、`crud.py`、`models.py`。
- 权限：`permissions.py`、`permission_migrations.py`。
- 项目管理：`Project`、`ProjectMember`、项目详情 8 Tab。
- 资料与版本：`Document`、`document_group_id`、`document_type`、`audience_scope`。
- 排班日历：访视模板、项目访视节点、日历事件、周排班。
- 资质整合：`integrations/` BFF 调用培训系统。
- Dataset：`backend/datasets/`、`frontend/dataset_pages.py`。
- Analysis：`backend/analysis/`、`frontend/analysis_pages.py`。
- Report：规划中。
- AI Workspace：规划中。

培训系统核心模块：

- 人员、仪器、培训记录、考核记录、授权记录。
- Excel 导入、操作日志、到期提醒、统计查询。
- 整合 API 供 Sub-I 查询资质。

### 1.5 两个子系统之间的关系

两个系统保持独立：

- 培训系统是资质事实源。
- Sub-I 不直接写培训系统数据库。
- Sub-I 通过 BFF 以服务账号调用培训 API。
- 两边人员通过 `employee_id` 关联。

这是一种清晰的联邦式边界：培训系统保留专业台账职责，Sub-I 只在项目工作流中查询和展示资质。

### 1.6 当前 Project 概念的存在形式

当前 Project 已经不是单纯文档标签，而是 Sub-I 平台的事实主轴：

```text
Project
├── Project 基本信息
├── ProjectMember 成员
├── Document 项目资料
├── Schedule 访视节点 / 日历 / 排班
├── Staff Qualification 资质视图（BFF 查询）
├── Dataset 数据集
├── AnalysisTask 分析任务
├── Report 规划
└── AI Workspace 规划
```

Project 的核心字段包括 `project_code`、`name`、`sponsor`、`claim_type`、`ethics_type`、`status`、`owner_employee_id`、`baseline_date` 等。`owner_employee_id` 已承担项目负责人和编辑权限的重要职责。

## 2. 当前架构优势分析

### 2.1 有利于未来扩展的设计

1. Project 已成为新能力挂载点  
   Dataset、Analysis、排班、资料、成员、资质都已围绕 `project_id` 展开，符合未来 Project 中心平台方向。

2. 双系统边界清楚  
   培训系统不并入 Sub-I，避免把培训、授权、项目研究数据混成一个大而脆弱的单体。

3. BFF 整合方式合理  
   Sub-I 前端只调用 8001，培训服务账号只在 Sub-I 后端配置，降低了前端泄露培训凭据和跨系统耦合风险。

4. 资料版本与资料类型已有基础  
   `document_group_id`、`document_type`、`content_text` 为 Protocol/SAP/CRF/Raw Data/Statistical Report 识别、报告生成和 AI 检索提供了基础。

5. Dataset 和 Analysis 已采用独立域模块  
   `backend/datasets/`、`backend/analysis/` 已经体现了未来新增分析能力时应使用的模块化落点。

6. 统计分析已有留痕意识  
   `AnalysisTask.result_json` 和 `log_json` 记录分析结果、参数、包版本、数据集信息，为可重复计算和人工审核奠定基础。

7. 权限模型已有项目层基础  
   `User.role`、`Project.owner_employee_id`、`ProjectMember`、`audience_scope`、`AuditLog` 和通知机制，已经能支撑基本项目可见性与负责人责任边界。

### 2.2 值得保留的设计

- 四容器、双系统独立部署。
- 业务数据与代码分离。
- Sub-I BFF 查询培训系统，不直接写培训数据库。
- Project 下扩展新能力，而不是新建第三套应用。
- 规则/统计层与 AI 层分离。
- AI 只能辅助草稿、解释和润色，不能无人审核定稿。
- Word 报告以 docx 模板生成，最终归档为项目 Document。

### 2.3 已具备平台化基础的模块

- 项目管理：已有项目台账、负责人、成员、详情多 Tab。
- 资料库：已有项目资料、通用资料、版本组和资料类型。
- 排班日历：已有项目访视节点、日历事件和排班关联。
- 资质整合：已有人员资质联邦查询。
- Dataset：已有 Excel 上传、sheet 预览、列映射、状态确认。
- Analysis：已有规则执行入口、标准分析类型、结果和日志。

## 3. 面向 Project 中心架构的适配性分析

目标结构：

```text
Project
├── 项目基本信息
├── 研究方案
├── 受试者
├── 时间点
├── 样品
├── 仪器检测
│   ├── VISIA
│   ├── OCT
│   └── 其他设备
├── 原始数据
├── 分析结果
├── 统计分析
├── AI解释
└── 报告输出
```

### 3.1 当前架构是否支持这种演进

结论：当前架构支持渐进演进，但还不完整。

支持点：

- Project 已经是 Sub-I 的主轴。
- 资料、排期、人员资质、Dataset、Analysis 都已挂到 Project。
- `document_type` 可承载 Protocol、SAP、CRF、Raw Data、Statistical Report 等研究资料类型。
- Dataset 可作为原始数据和整理后数据的第一层抽象。
- AnalysisTask 可作为统计分析和功效评价结果的第一层抽象。
- Report 和 AI Workspace 已在文档与页面信息架构中预留。

不足点：

- 尚无 Subject 受试者实体。
- 尚无 Sample 样品实体。
- 尚无 InstrumentMeasurement / DeviceData 这类仪器检测实体。
- 当前时间点主要存在于排班访视节点和 Dataset 映射中，还不是统一的研究时间点模型。
- 当前 Dataset 以 Excel 为主，尚未抽象多仪器原始文件、设备参数、图像文件、测量批次等信息。
- AnalysisTask 更偏统计任务，不足以直接表达 VISIA/OCT 等仪器算法分析流水线。

### 3.2 已具备基础的部分

| 目标能力 | 当前基础 | 适配程度 |
|----------|----------|----------|
| 项目基本信息 | `projects` 表 | 高 |
| 研究方案 | `Document.document_type=Protocol/SAP/CRF` | 中高 |
| 时间点 | `project_visit_nodes`、Dataset 访视映射 | 中 |
| 原始数据 | `Document.document_type=Raw Data`、`Dataset` | 中 |
| 分析结果 | `AnalysisTask.result_json` | 中 |
| 统计分析 | Analysis engine | 中高 |
| 报告输出 | Report 文档规划、Document 归档规则 | 中 |
| AI解释 | `content_text`、AI Workspace 规划 | 初步 |
| 资质支持 | BFF 查询培训授权 | 高 |

### 3.3 未来可能成为瓶颈的部分

1. 受试者与样品缺少核心实体  
   未来多仪器、多时间点分析必须稳定关联受试者、样品、访视、检测记录。仅靠 Excel 列映射会逐渐不够。

2. 仪器数据缺少统一抽象  
   VISIA、OCT、皮肤检测仪等可能产生图像、数值、报告、设备参数和导出文件。当前 Dataset 适合结构化 Excel，不足以管理复杂设备数据生命周期。

3. 时间点模型分散  
   排班访视节点、Dataset 的访视列、AnalysisTask 的 baseline/comparison_visit 目前没有统一引用同一张时间点表。

4. SQLite 长期扩展能力有限  
   对当前本地部署合理，但未来若数据量、附件索引、并发分析、审计查询增多，需要提前规划迁移边界。

5. `main.py` 仍承载较多核心路由  
   虽然新域已拆分，但项目、资料、用户仍集中在入口文件。继续扩展 Report/AI/Subject 时应保持模块拆分，避免入口变得更重。

6. Analysis engine 仍是内置标准分析  
   当前适合 2～3 种常用统计，但对于 VISIA/OCT 算法、图像处理、设备专属指标计算，需要更清晰的分析模块接口。

## 4. 数据模型评估

### 4.1 是否适合多项目、多仪器、多时间点管理

多项目：基本适合。

- `Project`、`ProjectMember`、`Document.project_id`、`Dataset.project_id`、`AnalysisTask.project_id` 已形成多项目结构。
- 权限也围绕项目负责人和项目成员展开。

多时间点：部分适合。

- 排班域已有 `VisitTemplateNode`、`ProjectVisitNode`、`CalendarEvent`。
- Dataset 映射中可识别访视列。
- AnalysisTask 有 baseline 和 comparison visit。
- 但时间点尚未形成统一的研究数据引用实体，未来同一个 Visit/Timepoint 在排班、样品、检测、统计之间可能需要统一标识。

多仪器：目前主要适合资质查询，不适合研究检测数据管理。

- 培训系统有 Instrument、TrainingRecord、AssessmentRecord、Authorization。
- Sub-I 能查询人员是否具备某仪器资质。
- 但 Sub-I 内尚无 ProjectInstrument、InstrumentMeasurement、DeviceDataset 等研究数据实体。

### 4.2 项目、用户、数据、分析结果关系是否合理

当前关系总体合理：

```text
User
├── role / job_title
├── Project.owner_employee_id
└── ProjectMember.employee_id

Project
├── Document
├── Dataset
└── AnalysisTask
    └── Dataset
```

优点：

- 用户权限不依赖业务职务，`role` 与 `job_title` 分离合理。
- 项目负责人由 `owner_employee_id` 驱动，适合实际项目责任制。
- Dataset 必须属于 Project，AnalysisTask 必须属于 Project 和 Dataset，链路清楚。
- AnalysisTask 的 `result_json` / `log_json` 使结果和执行过程可追溯。

需要逐步优化：

- `employee_id` 在多个表中以字符串引用，当前简单实用，但未来跨系统同步、离职、同名、工号变更时需要治理策略。
- 多个 JSON 字段适合早期快速扩展，但未来关键查询字段应逐步结构化。
- Report 表仍未实现，报告和 AnalysisTask、Document 的闭环还只是规划。
- 当前没有把 AnalysisTask 的“人工审核”建模成完整审核流，只通过状态和 `reviewed_by` 表达。

### 4.3 未来需要拆分或抽象的数据实体

不建议现在一次性大规模加表，但未来可按业务成熟度逐步引入：

| 未来实体 | 作用 | 建议时机 |
|----------|------|----------|
| Subject | 管理受试者编号、入排标准、脱敏标识 | 开始正式受试者管理时 |
| StudyVisit / Timepoint | 统一研究时间点 | Dataset 与排班需要强关联时 |
| Sample | 管理样品编号、采集时间、关联受试者和访视 | 样品流转进入系统时 |
| ProjectInstrument | 项目使用仪器清单 | 多仪器检测计划明确时 |
| InstrumentMeasurement | 记录一次仪器检测 | 接入 VISIA/OCT 原始数据时 |
| DeviceDataFile | 管理设备原始文件、图像、导出文件 | 仪器文件上传增多时 |
| AnalysisResult / AnalysisArtifact | 结构化保存分析输出、图片、表格 | 分析类型增多时 |
| ReviewRecord | 审核意见、退回、定稿留痕 | Report/AI 草稿进入审核流程时 |
| AIActionLog | AI 输入、引用资料、输出、人工采纳情况 | AI Workspace 启动时 |

### 4.4 当前可以保持的部分

- `Project` 作为根对象。
- `Document` 同时承载通用资料和项目资料，继续使用 `project_id IS NULL` 表示通用库。
- `ProjectMember` 作为成员关系。
- `Dataset` 作为第一阶段结构化数据入口。
- `AnalysisTask` 作为标准统计任务入口。
- 培训系统中的仪器资质数据继续作为外部事实源。

### 4.5 未来需要逐步优化的部分

- 将研究时间点从文本/映射逐步对齐到项目访视节点。
- 将仪器检测从 Excel Dataset 逐步抽象为设备数据记录。
- 将关键 JSON 中需要查询、统计和审核的字段逐步结构化。
- 将 Report 审核和 AI 辅助输出纳入明确状态机和审计表。
- 为数据库迁移建立更统一的版本化策略，尤其是 Sub-I 当前 `ensure_*` 启动迁移模式。

## 5. 模块化和扩展能力评估

### 5.1 是否可以采用“核心平台 + 分析模块插件”

可以，但建议先采用“内部模块插件化”的渐进模式，而不是立即引入复杂插件框架。

推荐目标形态：

```text
核心平台
├── Project / User / Permission
├── Document / Dataset / Report
├── Review / Audit
└── Analysis Registry
    ├── standard_stats
    ├── visia_analysis
    ├── oct_analysis
    ├── questionnaire_analysis
    └── custom_effectiveness_rules
```

当前 Analysis engine 已具备雏形：

- `runner.py` 统一执行入口。
- `ANALYSIS_TYPES` 注册分析类型。
- `stats_utils.py` 承载统计工具。
- `result_json` / `log_json` 承载结果和留痕。

### 5.2 当前代码对该方向的支持程度

支持点：

- Analysis 已独立于 `main.py`，有自己的 routes、crud、migrations、engine。
- API 已按 `/projects/{id}/analysis` 组织。
- 结果输出已结构化。
- Dataset 与 Analysis 解耦，Analysis 引用已确认 Dataset。

不足点：

- 分析类型注册仍是简单字典和 `if` 分支，不是标准接口。
- 设备专属输入、输出、依赖、可视化、质量控制、参数表单尚无统一协议。
- 分析任务状态较简单，还未覆盖“待审核 / 已审核 / 已定稿 / 已归档”等流程。
- 尚无分析结果产物管理，如图片、导出表、算法版本、设备版本等。

### 5.3 对未来新增能力的适配判断

| 能力 | 当前适配性 | 说明 |
|------|------------|------|
| VISIA 分析 | 中低 | 需图像/设备导出文件实体和设备算法模块 |
| OCT 分析 | 中低 | 需支持图像/层厚/扫描参数等专属结构 |
| 皮肤检测仪器分析 | 中 | 若导出 Excel，可先走 Dataset；若有图像则需扩展 |
| 问卷分析 | 中高 | 适合先作为 Dataset + Analysis 类型扩展 |
| 常规统计分析 | 中高 | 当前已有标准分析基础 |
| 功效评价 | 中 | 可基于 AnalysisTask 扩展规则，但需明确评价规则和审核 |

### 5.4 渐进式建议

- 近期不引入外部插件系统。
- 先把 Analysis engine 内部接口稳定下来，例如每类分析具备 `validate_input`、`run`、`build_result_table`、`build_log`。
- 新增分析能力时仍落在 `backend/analysis/engine/` 或子目录中，并通过 registry 暴露。
- 当 VISIA/OCT 等设备数据稳定后，再抽象设备数据模块，而不是一开始为所有仪器设计复杂通用模型。

## 6. AI 能力接入准备度评估

### 6.1 当前是否具备基础

当前具备 AI 接入的基础，但还不适合直接开发“自动结论”或“全自动报告”。

已有基础：

- Document 已有 `document_type` 和 `content_text`，可支持 Protocol/SAP/CRF 的检索和理解。
- Project 已聚合资料、数据集、分析任务和未来报告。
- AnalysisTask 有规则计算结果和 `log_json` 留痕。
- 文档明确规定 AI 不得自动定稿统计结论和最终报告。
- Report 规划明确采用模板填充、人工审核、归档为 Document。

缺口：

- 尚无 AIActionLog 或 AI 输出审计表。
- 尚无项目资料索引策略。
- 尚无 AI 输出与来源资料、分析任务、人工采纳记录的关联模型。
- 尚无 Prompt/模型版本/引用来源记录规范。
- 尚无 AI 草稿进入审核流程的状态设计。

### 6.2 数据和代码分离

当前数据与代码分离做得较好：

- 业务数据库和附件不进入 Git。
- `.env` 不打印、不提交、不覆盖。
- 部署文档明确生产数据保护边界。

AI 接入时应延续该原则：

- 不把真实研究数据、附件、密钥写入代码或模板。
- AI 索引数据应存储在业务数据目录或数据库中，并纳入备份策略。
- AI 调用日志应避免保存不必要的敏感全文，至少区分引用摘要、文档 ID、片段位置和输出结果。

### 6.3 AI 和业务规则分离

当前文档已明确“三层分离”：

```text
AI 层：理解 Protocol/SAP，生成建议或草稿
规则/统计层：可重复计算、留痕、与外部工具对照
报告层：模板填充、人工审核、归档
```

这条原则非常适合保留。未来 AI 能力应只做：

- 提取研究设计、终点、访视和统计方法。
- 生成分析计划草稿。
- 对已由规则引擎产生的结果做解释草稿。
- 辅助报告 Results 章节润色。
- 做项目内资料问答。

AI 不应做：

- 最终 P 值确认。
- 样本剔除定稿。
- 统计结论定稿。
- 无审核签发报告。
- 绕过 AnalysisTask 直接写入最终结论。

### 6.4 规则引擎与人工审核

当前 Analysis 已经是规则引擎雏形，但人工审核流程仍较轻：

- 目前状态有“草稿 / 已执行 / 已驳回”。
- 有 `reviewed_by` 字段。
- 还缺少审核意见、审核时间、审核动作、定稿锁定等完整流程。

Report 阶段应优先补齐“待审 / 定稿 / 版本化 / 归档”的闭环，再接入 AI 草稿能力。否则 AI 输出容易绕开人工审核边界。

## 7. 当前最值得优化的 5 个基础问题

### P0：必须优先处理

1. 明确 Report 阶段的审核与归档闭环  
   Report 是下一阶段重点，应先确保模板生成、Analysis 结果引用、人工审核、定稿归档为 Document 的链路清楚。风险在于如果先接 AI，容易形成“AI 直接写结论”的不安全路径。

2. 防止新域继续堆叠到 `backend/main.py` 和 `frontend/app.py`  
   当前入口文件已经较重。Report、AI、未来 Subject/InstrumentData 都应保持独立模块，否则后续平台化会快速变得难维护。

### P1：建议近期处理

3. 统一研究时间点的引用策略  
   当前访视节点、Dataset 映射、AnalysisTask 的访视字段尚未统一。建议先建立“Dataset/Analysis 访视值如何对应 ProjectVisitNode”的规则，不必马上大改表。

4. 稳定 Analysis engine 的内部扩展接口  
   在新增 VISIA/OCT/问卷分析前，先抽象分析类型注册、输入校验、执行、结果表、日志输出的内部约定。保持小步演进即可，不需要引入复杂插件市场。

### P2：未来考虑

5. 规划受试者、样品、仪器检测实体  
   当前尚可用 Dataset 和 Document 承载早期数据，但未来多仪器、多时间点、多样品后，应逐步引入 Subject、Sample、InstrumentMeasurement 等实体。建议等真实仪器接入流程明确后再做，避免过度设计。

## 8. 不建议现在做的事情

### 8.1 当前不应该重构的部分

- 不应整体重写 Sub-I。
- 不应把培训系统合并进 Sub-I。
- 不应拆掉现有四容器部署。
- 不应迁移全部 SQLite 到大型数据库，除非已经出现明确容量、并发或运维瓶颈。
- 不应重写已可用的资料库、排班、权限、Dataset、Analysis。
- 不应为了“插件化”立即引入复杂插件框架或微服务架构。

### 8.2 不应该提前开发的功能

- 完整 LIMS。
- 每人独立子库。
- AI 全自动生成最终统计结论。
- AI 自动签发报告。
- 全自动 CSR。
- 拖拽式甘特图或 MS Project 级项目管理。
- 大而全的多租户 SaaS 架构。
- 未明确输入格式前的 VISIA/OCT 全量自动对接。

### 8.3 可能造成过度设计的方向

- 在没有真实设备文件样本前设计通用仪器数据平台。
- 在 Report 审核闭环未完成前做 AI 报告生成。
- 在 Subject/Sample 业务流程未稳定前一次性建立完整临床数据仓库。
- 为少量内部用户过早引入 Kubernetes、消息队列、分布式任务系统。
- 把所有 JSON 字段立即拆成大量表，导致开发成本过高。

## 9. 推荐未来 6-12 个月演进路线

### 阶段 1：基础架构优化

目标：

- 保持现有系统可用。
- 持续文档与代码一致性维护。
- 防止新域堆叠到主入口。
- 梳理 Report 模块的最小闭环设计。

收益：

- 降低后续新增模块的维护成本。
- 保住当前业务连续性。
- 为 Report、AI、仪器分析留下清晰落点。

风险：

- 如果只整理文档、不形成模块边界约束，后续开发仍可能回到入口文件堆叠。
- 如果过度整理，可能影响当前稳定功能。

建议产出：

- Report 最小数据模型与审核状态说明。
- Analysis engine 内部扩展约定。
- Dataset/Analysis 与 ProjectVisitNode 的映射规则。

### 阶段 2：Project 中心化

目标：

- 完成 Report 第一版：模板、Analysis 结果填表、docx 生成、人工审核、归档为项目 Document。
- 强化项目详情 8 Tab 的实际工作流。
- 将研究方案、数据、分析、报告在 Project 下形成闭环。

收益：

- Project 从“资料和排班中心”升级为“研究交付中心”。
- 统计报告可追溯到 Dataset 和 AnalysisTask。
- 为后续 AI 解释提供可靠上下文。

风险：

- 报告生成如果过早追求复杂排版，会拖慢落地。
- 审核流程如果过轻，后续 AI 接入存在合规风险。

建议产出：

- `backend/reports/` 和 `frontend/report_pages.py`。
- 报告状态流：草稿 → 待审 → 定稿。
- 生成日志和来源分析任务记录。
- 定稿报告自动归档为 Document。

### 阶段 3：分析能力模块化

目标：

- 将现有 Analysis engine 梳理为可扩展的内部分析模块机制。
- 新增问卷分析、功效评价规则或特定仪器导出 Excel 的分析能力。
- 根据真实需求逐步探索 VISIA/OCT 数据接入。

收益：

- 新分析类型可控扩展。
- 统计规则和设备算法可以独立演进。
- 结果格式逐步稳定，方便 Report 和 AI 复用。

风险：

- 如果过早抽象所有设备，可能导致模型复杂但无真实使用。
- 如果每个分析都自由写结果 JSON，Report 和 AI 会难以统一消费。

建议产出：

- Analysis registry。
- 每类分析统一输入校验、执行、结果表、日志协议。
- 分析产物管理策略。
- 第一类设备/问卷分析试点。

### 阶段 4：AI 辅助能力接入

目标：

- 启动 AI Workspace 第一版。
- 读取项目 Protocol/SAP/CRF 等资料。
- 生成分析计划草稿、结果解释草稿、报告文字润色。
- 记录 AI 引用来源、输出和人工采纳情况。

收益：

- 降低资料阅读、分析计划起草和报告初稿撰写成本。
- AI 能围绕 Project 上下文工作，而不是孤立聊天。
- 保留规则计算和人工审核底线。

风险：

- 若缺少 AIActionLog 和审核流，AI 输出可能难以追溯。
- 若直接让 AI 生成结论，会违反当前系统边界和临床研究风险控制原则。

建议产出：

- `backend/ai_workspace/`、`frontend/ai_workspace.py`。
- AIActionLog 或等价审计记录。
- 项目资料索引策略。
- AI 输出必须标记“草稿 / 建议”，不得覆盖规则引擎结果和定稿报告。

---

## 总体结论

当前项目已经具备向 Project 中心临床研究平台演进的良好基础：Project 主轴、资料版本、权限、排班、资质 BFF、Dataset、Analysis 等关键骨架已经存在，且双系统独立和业务数据保护边界清楚。

最适合的演进方式不是推翻重建，而是继续沿着“Project 下挂新能力”的路线小步推进。近期重点应放在 Report 闭环、Analysis 扩展接口、时间点映射规则和审核留痕上。AI 能力可以作为后续增强层接入，但必须建立在规则计算、模板报告和人工审核之上，不能替代统计判断和最终定稿。
